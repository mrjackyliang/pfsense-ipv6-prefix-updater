See the protections the package applies before it changes your configuration and what can still affect traffic.

## What Happens on a Prefix Change

When the package finds a <Terminology title="Your prefix changed, so the package goes to work" to="/docs/reference/terminology#baselines-and-transitions">prefix transition</Terminology>, it works in this order:

1. Reads the <Terminology title="A public IPv6 address in 2000::/3, the only kind used" to="/docs/reference/terminology#addresses-and-prefixes">global address</Terminology> of each <Terminology title="The interface whose address reveals your current prefix" to="/docs/reference/terminology#interfaces-and-detection">Monitored Interface</Terminology> and calculates its prefix.
2. Compares the prefix with the <Terminology title="The stored prefix each check compares against" to="/docs/reference/terminology#baselines-and-transitions">last successful prefix</Terminology>.
3. Finds the <Terminology title="A setting the package is allowed to rewrite" to="/docs/reference/terminology#fields-and-change-plans">approved fields</Terminology> that still use the old prefix and builds the complete <Terminology title="Every planned rewrite, built before anything changes" to="/docs/reference/terminology#fields-and-change-plans">change plan</Terminology>.
4. Confirms that pfSense can reload every affected service and that no planned field has changed since it was read.
5. Saves a <Terminology title="A copy of the config taken right before any write" to="/docs/reference/terminology#backups-and-service-reloads">configuration backup</Terminology>.
6. Applies every change and saves the configuration once.
7. Checks the saved values, reloads only the affected services, and checks the values again.
8. Moves the <Terminology title="The recorded starting prefix that changes are measured from" to="/docs/reference/terminology#baselines-and-transitions">baseline</Terminology> to the new prefix, records the result, and sends a <Terminology title="The alert sent after your addresses were updated" to="/docs/reference/terminology#notifications-and-logs">change notification</Terminology> if it's turned on.

If any step before the backup fails, the configuration stays as it was.

## What Never Causes a Write

The package doesn't change the configuration on these outcomes:

- <Terminology title="First look: a baseline is recorded, nothing changes" to="/docs/reference/terminology#run-outcomes">Initialized</Terminology> and <Terminology title="A dry run showing the baseline it would record" to="/docs/reference/terminology#run-outcomes">Initialization preview</Terminology>.
- <Terminology title="Same prefix as last time, so there is nothing to do" to="/docs/reference/terminology#run-outcomes">No change</Terminology>.
- <Terminology title="A preview of the changes that writes nothing" to="/docs/reference/terminology#running-checks">Dry run</Terminology>.
- <Terminology title="Prefix changed, but no approved field used the old one" to="/docs/reference/terminology#run-outcomes">Warning</Terminology>.
- A <Terminology title="The run stopped at a check or safety stage" to="/docs/reference/terminology#run-outcomes">Failure</Terminology> that stops before the backup.

## What Can Still Affect Traffic

- **<Terminology title="Applies changed settings to a running service" to="/docs/reference/terminology#backups-and-service-reloads">Service reloads</Terminology>**: changes to static interfaces or <Terminology title="An extra address on an interface, such as a CARP VIP" to="/docs/reference/terminology#pfsense-features">virtual IPs</Terminology> reload every interface and then the firewall filter. Gateway and static route changes reload routing and the filter, OpenVPN changes reload every OpenVPN instance, and DHCPv6, router advertisement, and DNS changes restart those services.
- **Failures after the save**: if a check or <Terminology title="Applies changed settings to a running service" to="/docs/reference/terminology#backups-and-service-reloads">service reload</Terminology> fails after the save, the new values stay saved and nothing is rolled back. The <Terminology title="The recorded starting prefix that changes are measured from" to="/docs/reference/terminology#baselines-and-transitions">baseline</Terminology> stays on the old prefix, as [Run Outcomes](/docs/operate/run-outcomes#failures-after-the-save) explains.
- **Values that wait for you**: gateways, static routes, DNS domain overrides, and the other values in [Other Settings](/docs/configure/configuration-scopes#other-settings) keep the old prefix until you tick them, and so do fields in a group that is off.

## Recovery Path

Every write has a <Terminology title="A copy of the config taken right before any write" to="/docs/reference/terminology#backups-and-service-reloads">configuration backup</Terminology> of the configuration before it in <Terminology title="pfSense's saved config revisions you can restore" to="/docs/reference/terminology#backups-and-service-reloads">Config History</Terminology>. The revision named after the package holds the updated configuration, so [Backups and Recovery](/docs/operate/backups-and-recovery) shows which revision to restore.

It is recommended to keep your usual off-device pfSense backups as well.

## What You Can Verify

The Status tab shows the <Terminology title="The live address the prefix is read from on each run" to="/docs/reference/terminology#interfaces-and-detection">source address</Terminology>, <Terminology title="The prefix seen right now, compared with the last one" to="/docs/reference/terminology#interfaces-and-detection">observed prefix</Terminology>, outcome, changed-field count, backup result, <Terminology title="Applies changed settings to a running service" to="/docs/reference/terminology#backups-and-service-reloads">reloaded services</Terminology>, time, and summary of the latest run. The <Terminology title="The latest run's lines, shown right after you start it" to="/docs/reference/terminology#running-checks">Command Output</Terminology> shows the same details right after a <Terminology title="A check you start yourself, even with schedules off" to="/docs/reference/terminology#running-checks">manual run</Terminology>.
