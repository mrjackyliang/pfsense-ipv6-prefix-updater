Follow one run from reading the interface addresses to recording the result, including every point where it can stop.

## 1. Read and Validate

- A scheduled check stops right away as <Terminology title="A scheduled check skipped because scheduled updates are off" to="/docs/reference/terminology#run-outcomes">Disabled</Terminology> when **<Terminology title="Automatic checks on a schedule, off until you enable them" to="/docs/reference/terminology#running-checks">Enable Scheduled Updates</Terminology>** is off. A <Terminology title="A check you start yourself, even with schedules off" to="/docs/reference/terminology#running-checks">manual run</Terminology> continues.
- The run checks the saved settings again, because they could have changed since the form was saved.
- It reads the <Terminology title="A public IPv6 address in 2000::/3, the only kind used" to="/docs/reference/terminology#addresses-and-prefixes">global address</Terminology> of each <Terminology title="The interface whose address reveals your current prefix" to="/docs/reference/terminology#interfaces-and-detection">Monitored Interface</Terminology> fresh, without a <Terminology title="An fe80 address that is never used as a source" to="/docs/reference/terminology#addresses-and-prefixes">link-local address</Terminology> fallback, and converts it to <Terminology title="The short lowercase spelling, such as 2001:db8::1" to="/docs/reference/terminology#addresses-and-prefixes">canonical form</Terminology>.
- It masks each address at its row's <Terminology title="How big your ISP's prefix is, like /56; you set it" to="/docs/reference/terminology#addresses-and-prefixes">Delegated Prefix Length</Terminology> to get the <Terminology title="The prefix seen right now, compared with the last one" to="/docs/reference/terminology#interfaces-and-detection">observed prefix</Terminology>.

## 2. Compare

- With no <Terminology title="The recorded starting prefix that changes are measured from" to="/docs/reference/terminology#baselines-and-transitions">baseline</Terminology> for the interface, the run records one and ends as <Terminology title="First look: a baseline is recorded, nothing changes" to="/docs/reference/terminology#run-outcomes">Initialized</Terminology>.
- When the prefix and its length match the <Terminology title="The stored prefix each check compares against" to="/docs/reference/terminology#baselines-and-transitions">last successful prefix</Terminology>, the run ends as <Terminology title="Same prefix as last time, so there is nothing to do" to="/docs/reference/terminology#run-outcomes">No change</Terminology> without scanning the configuration.
- A different prefix or length is a <Terminology title="Your prefix changed, so the package goes to work" to="/docs/reference/terminology#baselines-and-transitions">prefix transition</Terminology>, and the run continues.

## 3. Plan

- The run reads the configuration through pfSense's configuration functions and keeps only the fields selected on the Fields tab. Selected fields that no longer exist are skipped and listed under **Skipped Fields**.
- Each address in an <Terminology title="A setting the package is allowed to rewrite" to="/docs/reference/terminology#fields-and-change-plans">approved field</Terminology> that belongs to the old prefix, at the stored length, gets the new prefix bits at the current length and keeps its <Terminology title="The bits after the prefix, always copied unchanged" to="/docs/reference/terminology#addresses-and-prefixes">host portion</Terminology>. Together these changes form the complete <Terminology title="Every planned rewrite, built before anything changes" to="/docs/reference/terminology#fields-and-change-plans">change plan</Terminology>.
- With nothing to change, the run ends as <Terminology title="Prefix changed, but no approved field used the old one" to="/docs/reference/terminology#run-outcomes">Warning</Terminology>. A <Terminology title="A preview of the changes that writes nothing" to="/docs/reference/terminology#running-checks">dry run</Terminology> with changes ends here as <Terminology title="A preview of the changes that writes nothing" to="/docs/reference/terminology#running-checks">Dry run</Terminology>.

## 4. Preflight

- The run confirms that pfSense can reload every service in the plan. <Terminology title="The address on a WireGuard tunnel interface" to="/docs/reference/terminology#pfsense-features">WireGuard tunnel addresses</Terminology> need the WireGuard package for this.
- It confirms that each planned field still holds the value it had when the plan was built.

## 5. Back Up and Write Once

- pfSense creates a <Terminology title="A copy of the config taken right before any write" to="/docs/reference/terminology#backups-and-service-reloads">configuration backup</Terminology>, and the run stops if pfSense doesn't confirm it.
- The run applies every change and saves once, with the description `IPv6 Prefix Updater changed <count> approved field(s) for interface <interface>`.
- If pfSense reports the save as failed, the run puts the original values back in memory and stops.

## 6. Verify, Reload, Verify

- The run checks that the saved values match the plan, reloads the affected services, and checks the values again.
- Services reload in the fixed order that [Reload Actions](/docs/reference/approved-fields#reload-actions) lists, from Interfaces to WireGuard. An Interfaces reload is followed by a firewall filter reload, which then isn't repeated.
- The firewall filter, DNS Resolver, and DNS Forwarder reloads fail the run when they return a failure. The other reloads fail it only when they raise an error.
- Other packages' settings are applied again last, after the reloads and their verification. A package that can't be applied is reported, and the saved values stay.
- A failure in this stage leaves the new values saved.

## 7. Record and Notify

- The <Terminology title="The recorded starting prefix that changes are measured from" to="/docs/reference/terminology#baselines-and-transitions">baseline</Terminology> moves to the new prefix, and **Last Run** records the <Terminology title="Prefix changed and every approved field was updated" to="/docs/reference/terminology#run-outcomes">Success</Terminology> with the changed-field count and the <Terminology title="Applies changed settings to a running service" to="/docs/reference/terminology#backups-and-service-reloads">reloaded services</Terminology>.
- The run writes a <Terminology title="pfSense's general log, where every run leaves lines" to="/docs/reference/terminology#notifications-and-logs">system log</Terminology> line and sends a <Terminology title="The alert sent after your addresses were updated" to="/docs/reference/terminology#notifications-and-logs">change notification</Terminology> if it's turned on. A failed notification doesn't change the outcome.
