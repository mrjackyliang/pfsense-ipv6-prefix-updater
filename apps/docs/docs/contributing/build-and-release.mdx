Check, stage, and package IPv6 Prefix Updater for pfSense, then publish the package to a GitHub release.

## Requirements

- **Node.js 22, 24, or 26** — The root and workspace manifests accept `^22 || ^24 || ^26`.
- **PHP or Docker** — The PHP suites use a local `php` when one exists, or the `php:8.3-cli-alpine` image through Docker. `PHP_TEST_IMAGE` overrides the image.
- **FreeBSD for packaging** — `npm run deploy` runs only on FreeBSD, with `PFSENSE_PORTS_DIR` pointing at a pfSense FreeBSD-ports checkout.

## Check, Stage, and Package

Run these commands from the repository root:

```bash
# Lint and type-check the scripts, run the PHP and Vitest suites, and validate the port.
npm run check --workspace pfsense-pkg-ipv6-prefix-updater

# Copy the port into packages/ipv6-prefix-updater/build/port with the workspace version.
npm run build --workspace pfsense-pkg-ipv6-prefix-updater

# Build the package on FreeBSD into packages/ipv6-prefix-updater/build/release.
PFSENSE_PORTS_DIR=/path/to/FreeBSD-ports npm run deploy --workspace pfsense-pkg-ipv6-prefix-updater
```

- Staging turns `port/Makefile.template` into `build/port/Makefile` and stamps it with the `version` from `packages/ipv6-prefix-updater/package.json`.
- Packaging copies the staged port to `sysutils/pfSense-pkg-Ipv6PrefixUpdater` in the ports checkout, runs `make package`, and removes that copy again. It stops if the destination already exists.
- `build/release` then holds the versioned `.pkg`, a copy named `pfSense-pkg-Ipv6PrefixUpdater.pkg`, and a `.sha256` file for each that contains only the hash.

## Release Workflow

The `publish-pfsense-packages-ipv6-prefix-updater` job in `.github/workflows/nova-publish-project.yml`, generated by Nova, runs for the publish workflow:

1. Validates and stages the port on an Ubuntu runner.
2. When the `PFSENSE_RELEASE_SIGNING_KEY` secret is set, derives the public key from `PFSENSE_RELEASE_SIGNING_KEY` and appends it to the staged port's `usr/local/share/pfSense-pkg-Ipv6PrefixUpdater/release-signing.pub` file.
3. Builds the package on FreeBSD with the configured pfSense FreeBSD-ports checkout.
4. When the secret is set, signs each `.pkg` as `<file>.pkg.sig` with `ssh-keygen -Y sign -n pfSense-pkg-Ipv6PrefixUpdater`.
5. Uploads the packages, checksums, and signatures as a workflow artifact kept for 7 days and attaches the same files to the release.

The build marks the package for any FreeBSD version because it contains no compiled code, so one package installs on every supported pfSense release. `PFSENSE_FREEBSD_VERSION` only selects the FreeBSD release used by the build VM. The install guide's `pkg add` command fetches `pfSense-pkg-Ipv6PrefixUpdater.pkg` from whichever release GitHub marks as latest.

## Release Signing

The only signing setup is the `PFSENSE_RELEASE_SIGNING_KEY` repository secret containing an unencrypted OpenSSH Ed25519 private key.

1. In 1Password, choose **New Item → SSH Key → Generate a New Key → Ed25519**.
2. On the private key field, choose **Export**, select OpenSSH format, and leave the password empty.
3. Check the clipboard before saving the secret:

   ```bash
   pbpaste | head -1
   ```

   The command should print `-----BEGIN OPENSSH PRIVATE KEY-----`.

4. Send the clipboard directly to GitHub, or read an exported file:

   ```bash
   pbpaste | gh secret set PFSENSE_RELEASE_SIGNING_KEY
   gh secret set PFSENSE_RELEASE_SIGNING_KEY < <file>
   ```

5. Delete the exported private-key file after the secret is saved.

Without the secret, packages ship without a public key and releases are unsigned. To change keys, add the new `ssh-ed25519 ...` public key to `release-signing.pub`, publish one release while the old key is still the secret, then replace the secret with the new key.

If the signing key is lost, installed copies cannot authenticate a release from its replacement. Each affected installation needs the manual `pkg add -f` command once to install a package carrying the replacement public key.

## Test Update Endpoints in a VM

The CLI accepts two environment variables solely for controlled VM tests:

- `IPV6_PREFIX_UPDATER_RELEASES_API` replaces the latest-release API URL.
- `IPV6_PREFIX_UPDATER_DOWNLOAD_PREFIX` replaces the allowed asset URL prefix.

They are read only by `/usr/local/sbin/ipv6-prefix-updater`; they are never stored in package configuration or read directly by the WebGUI. Set all required overrides on the same CLI invocation:

```shell
IPV6_PREFIX_UPDATER_RELEASES_API=http://192.0.2.10/latest.json \
IPV6_PREFIX_UPDATER_DOWNLOAD_PREFIX=http://192.0.2.10/releases/ \
/usr/local/sbin/ipv6-prefix-updater --check-updates
```

Use `--self-update` instead of `--check-updates` to exercise the complete download, SHA-256, release-signature, package-metadata, and `pkg add -f` path against the test release.

## Documentation Site

From `apps/docs`, `npm run check` runs ESLint, the translation tree check, three type checks, and the Vitest suites for `.env` files, frontmatter, links, tables, glossary links, and type declarations. `npm run build` builds every locale.

Each locale's translated docs pages live in `apps/docs/i18n/<locale>/docusaurus-plugin-content-docs/current/` and mirror the English pages, so update them when an English page changes. The interface text (homepage, navbar, footer, blog, and sidebar labels) comes from `scripts/generate-locales.mjs`, which reads `scripts/locale-copies.json` and the package translations. `npm run i18n` runs that generator first, and it leaves the translated docs pages in place.

`.github/workflows/nova-publish-project.yml` builds the site and deploys it to GitHub Pages when a release is published.
