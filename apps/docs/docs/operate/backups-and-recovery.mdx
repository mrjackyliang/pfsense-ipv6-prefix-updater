Find the configuration from before an update on the **Backups** tab or in pfSense's <Terminology title="pfSense's saved config revisions you can restore" to="/docs/reference/terminology#backups-and-service-reloads">Config History</Terminology> and restore it with pfSense's own tools.

## When a Backup Is Created

The package creates a <Terminology title="A copy of the config taken right before any write" to="/docs/reference/terminology#backups-and-service-reloads">configuration backup</Terminology> only on a run that writes, right before it changes any field. **<Terminology title="A copy of the config taken right before any write" to="/docs/reference/terminology#backups-and-service-reloads">Configuration Backup Created</Terminology>** on the Status tab shows whether the latest run made one.

No backup is created when a run ends as:

- <Terminology title="First look: a baseline is recorded, nothing changes" to="/docs/reference/terminology#run-outcomes">Initialized</Terminology> or <Terminology title="A dry run showing the baseline it would record" to="/docs/reference/terminology#run-outcomes">Initialization preview</Terminology>.
- <Terminology title="Same prefix as last time, so there is nothing to do" to="/docs/reference/terminology#run-outcomes">No change</Terminology>.
- <Terminology title="A preview of the changes that writes nothing" to="/docs/reference/terminology#running-checks">Dry run</Terminology>.
- **Accepted**, because accepting the current prefix changes only the package's <Terminology title="The file holding each baseline, kept across reinstalls" to="/docs/reference/terminology#running-checks">package state</Terminology>.
- <Terminology title="Prefix changed, but no approved field used the old one" to="/docs/reference/terminology#run-outcomes">Warning</Terminology>.
- <Terminology title="The run stopped at a check or safety stage" to="/docs/reference/terminology#run-outcomes">Failure</Terminology> before the backup stage, such as a settings, address, or reload capability problem.

## Backups Tab

**Services → IPv6 Prefix Updater → Backups** lists the package's own copies of `config.xml`, newest first. They stay available after pfSense rotates older revisions out of <Terminology title="pfSense's saved config revisions you can restore" to="/docs/reference/terminology#backups-and-service-reloads">Config History</Terminology>.

<img src={backupList} alt="IPv6 Prefix Updater Backups tab listing package backups taken before prefix updates and before a legacy migration, plus backups imported from the legacy updater, each with Download and Delete actions" width={1024} height={768} style={{maxWidth: '100%', height: 'auto'}} />

- **Before prefix update**: taken right before a run writes. **Details** names each interface's old and new prefix.
- **Before 1.x move**: taken before the package [moved the legacy updater](/docs/migrate-from-legacy) into its settings.
- **1.x script**: a backup the <Terminology title="Version 1.x: the update.php script run by Cron" to="/docs/reference/terminology#package-origins">legacy updater</Terminology> made, imported with its original name and time.

Only the newest 10 package backups are kept, while imported legacy backups stay until you delete them. Every backup is stored in `/cf/conf/ipv6-prefix-updater/backups`, readable by root only, and survives reboots and package removal.

To restore one, select **Download**, then upload the file under **Diagnostics → Backup & Restore → Restore Backup**. Restoring replaces the whole configuration, so the warnings below apply to these files too.

## How the Revisions Are Labelled

Each update leaves two revisions in <Terminology title="pfSense's saved config revisions you can restore" to="/docs/reference/terminology#backups-and-service-reloads">Config History</Terminology>, and only the older one undoes the update:

- **The configuration before the update**: the <Terminology title="A copy of the config taken right before any write" to="/docs/reference/terminology#backups-and-service-reloads">configuration backup</Terminology> is a copy of this revision. It keeps the description of whatever change was saved before the update.
- **The updated configuration**: the package saves its change as a new revision described as `IPv6 Prefix Updater changed <count> approved field(s) for interface <interface>`.

:::warning

The revision with the package's description holds the updated configuration. Restoring it doesn't undo the update.

:::

## Find the Right Revision

1. Open **Diagnostics → Backup & Restore → Config History**.
2. Find the newest revision described as `IPv6 Prefix Updater changed ... for interface ...`. If nothing was saved after the update, it is the current configuration.
3. Pick the revision saved directly before it, which is the configuration from before the update.
4. Compare the two revisions with the diff view. Apart from the revision details, only the fields counted in **Changed Fields** should differ.
5. Check whether other changes were saved after the update, because restoring an older revision removes them too.

## Restore the Revision

1. Use pfSense's restore action on the revision from before the update and follow its prompts.
2. Open **Services → IPv6 Prefix Updater → Settings** and check **<Terminology title="Automatic checks on a schedule, off until you enable them" to="/docs/reference/terminology#running-checks">Enable Scheduled Updates</Terminology>**, because the restored revision brings back the package settings from that time.
3. On the Status tab, select **<Terminology title="A preview of the changes that writes nothing" to="/docs/reference/terminology#running-checks">Dry Run</Terminology>** to see what the next run would do.

What the next run does depends on the outcome you are undoing:

- **After a <Terminology title="The run stopped at a check or safety stage" to="/docs/reference/terminology#run-outcomes">Failure</Terminology>**: the <Terminology title="The recorded starting prefix that changes are measured from" to="/docs/reference/terminology#baselines-and-transitions">baseline</Terminology> still holds the old prefix, so the next run plans the same update again.
- **After a <Terminology title="Prefix changed and every approved field was updated" to="/docs/reference/terminology#run-outcomes">Success</Terminology>**: the <Terminology title="The recorded starting prefix that changes are measured from" to="/docs/reference/terminology#baselines-and-transitions">baseline</Terminology> already holds the new prefix, so later runs report <Terminology title="Same prefix as last time, so there is nothing to do" to="/docs/reference/terminology#run-outcomes">No change</Terminology> and don't apply the update again. The restored addresses keep the old prefix until you change them.

:::warning

Restoring a revision replaces the whole configuration, including every change saved after that revision.

:::

## After a Failed Run

Start with **<Terminology title="A copy of the config taken right before any write" to="/docs/reference/terminology#backups-and-service-reloads">Configuration Backup Created</Terminology>** and **Summary** in the **Last Run** panel. A <Terminology title="The run stopped at a check or safety stage" to="/docs/reference/terminology#run-outcomes">Failure</Terminology> always shows `0` under **Changed Fields**, even when fields were already written.

- **<Terminology title="A copy of the config taken right before any write" to="/docs/reference/terminology#backups-and-service-reloads">Configuration Backup Created</Terminology> shows No**: the run stopped before writing, so the configuration is unchanged. [Troubleshooting](/docs/operate/troubleshooting#run-failed) lists the causes.
- **Summary reads `Run failed: pfSense could not write the planned configuration.`**: pfSense reported the write as failed. The package put the original values back in memory before it stopped.
- **Any other failure with a backup**: the new values are already saved, and nothing was rolled back. The <Terminology title="The recorded starting prefix that changes are measured from" to="/docs/reference/terminology#baselines-and-transitions">baseline</Terminology> still holds the old prefix, so later runs report <Terminology title="Prefix changed, but no approved field used the old one" to="/docs/reference/terminology#run-outcomes">Warning</Terminology> because the saved values no longer belong to it.

In the last case, choose the recovery that matches the saved configuration:

- **Apply the update again**: fix the failed check or reload, restore the revision from before the update, run a <Terminology title="A preview of the changes that writes nothing" to="/docs/reference/terminology#running-checks">Dry Run</Terminology>, and then select **Run Now**.
- **Keep the saved new-prefix values**: first verify the approved addresses and affected services yourself. Then open **Status → Actions → Baseline Recovery**, select **Accept Current Prefix**, and confirm the action.

**Accept Current Prefix** records the active source address, prefix, and prefix length as the new <Terminology title="The recorded starting prefix that changes are measured from" to="/docs/reference/terminology#baselines-and-transitions">baseline</Terminology>. It does not scan the firewall configuration, create a backup, write configuration, or reload a service; the outcome is **Accepted**, and the next ordinary check should report <Terminology title="Same prefix as last time, so there is nothing to do" to="/docs/reference/terminology#run-outcomes">No change</Terminology>.

:::warning

Do not accept the current prefix only to clear a warning. Accept it only after confirming every address that should use the new prefix is already correct and, after a reload failure, the affected service is operating with the saved configuration.

:::

If **Last Run** didn't change at all, the run stopped before it read its <Terminology title="The file holding each baseline, kept across reinstalls" to="/docs/reference/terminology#running-checks">package state</Terminology>. Its reason is in the <Terminology title="The latest run's lines, shown right after you start it" to="/docs/reference/terminology#running-checks">Command Output</Terminology> and the <Terminology title="pfSense's general log, where every run leaves lines" to="/docs/reference/terminology#notifications-and-logs">system log</Terminology>.

## Keep Off-Device Backups

<Terminology title="pfSense's saved config revisions you can restore" to="/docs/reference/terminology#backups-and-service-reloads">Config History</Terminology> is stored on the firewall itself. It is recommended to also download a backup from **Diagnostics → Backup & Restore** before you install or update the package or turn on <Terminology title="Automatic checks on a schedule, off until you enable them" to="/docs/reference/terminology#running-checks">scheduled updates</Terminology>.

## Preserve Evidence

Before restoring, it is recommended to copy the **Last Run** panel, the <Terminology title="The latest run's lines, shown right after you start it" to="/docs/reference/terminology#running-checks">Command Output</Terminology>, and the <Terminology title="pfSense's general log, where every run leaves lines" to="/docs/reference/terminology#notifications-and-logs">system log</Terminology> lines that start with `IPv6 Prefix Updater:`. Together they show which stage stopped and whether the configuration was written.

Review [Troubleshooting](/docs/operate/troubleshooting) for failure messages and [Check Before Automation](/docs/safety/testing-and-verification) before you turn the schedule back on.
