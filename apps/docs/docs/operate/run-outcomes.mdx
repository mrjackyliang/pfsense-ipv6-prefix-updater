It isn't recorded, so the Status tab never shows it.

## Current State Versus Last Run

**Current State** changes only on <Terminology title="First look: a baseline is recorded, nothing changes" to="/docs/reference/terminology#run-outcomes">Initialized</Terminology>, **Accepted**, and <Terminology title="Prefix changed and every approved field was updated" to="/docs/reference/terminology#run-outcomes">Success</Terminology>. A failed attempt never becomes the next comparison point unless an operator later verifies the saved values and explicitly accepts the active prefix; **Last Run** records the latest run of every outcome in the table.

**Last Run** stays as it was when another check holds the <Terminology title="Keeps two checks from ever running at once" to="/docs/reference/terminology#running-checks">run lock</Terminology> or when a run stops before reading its <Terminology title="The file holding each baseline, kept across reinstalls" to="/docs/reference/terminology#running-checks">package state</Terminology>, such as when no monitored interface has a <Terminology title="A public IPv6 address in 2000::/3, the only kind used" to="/docs/reference/terminology#addresses-and-prefixes">global address</Terminology>. Those runs leave their reason in the <Terminology title="The latest run's lines, shown right after you start it" to="/docs/reference/terminology#running-checks">Command Output</Terminology> and the <Terminology title="pfSense's general log, where every run leaves lines" to="/docs/reference/terminology#notifications-and-logs">system log</Terminology>.

## Warning: No Matching Fields

A <Terminology title="Prefix changed, but no approved field used the old one" to="/docs/reference/terminology#run-outcomes">Warning</Terminology> means the prefix changed, but none of the <Terminology title="A setting the package is allowed to rewrite" to="/docs/reference/terminology#fields-and-change-plans">approved fields</Terminology> belonged to the old prefix. Nothing is written and the <Terminology title="The recorded starting prefix that changes are measured from" to="/docs/reference/terminology#baselines-and-transitions">baseline</Terminology> stays on the old prefix, so the next run checks the same <Terminology title="Your prefix changed, so the package goes to work" to="/docs/reference/terminology#baselines-and-transitions">prefix transition</Terminology> again.

Each <Terminology title="Prefix changed, but no approved field used the old one" to="/docs/reference/terminology#run-outcomes">Warning</Terminology> adds a <Terminology title="An alert in pfSense's own notices list" to="/docs/reference/terminology#notifications-and-logs">WebGUI notice</Terminology>, including one from a <Terminology title="A preview of the changes that writes nothing" to="/docs/reference/terminology#running-checks">dry run</Terminology>. A cause that isn't fixed adds a new notice on every scheduled run.

Common causes:

- The <Terminology title="One switch for a whole kind of setting" to="/docs/reference/terminology#fields-and-change-plans">field group</Terminology> that holds the addresses is off, or the fields are unticked.
- The addresses were already changed outside the package.
- The addresses are in [Other Settings](/docs/configure/configuration-scopes#other-settings), which stays off until you tick them.
- An earlier <Terminology title="The run stopped at a check or safety stage" to="/docs/reference/terminology#run-outcomes">Failure</Terminology> saved the new values but kept the old <Terminology title="The recorded starting prefix that changes are measured from" to="/docs/reference/terminology#baselines-and-transitions">baseline</Terminology>.
- The <Terminology title="How big your ISP's prefix is, like /56; you set it" to="/docs/reference/terminology#addresses-and-prefixes">Delegated Prefix Length</Terminology> was [widened](/docs/configure/interface-and-prefix#changing-the-prefix-length) without a prefix change.

[Troubleshooting](/docs/operate/troubleshooting#warning-on-every-run) covers each cause.

If the addresses were already changed correctly, use **Status → Actions → Baseline Recovery → Accept Current Prefix** after verifying the saved addresses and affected services. This records an **Accepted** outcome without scanning approved fields or changing firewall configuration; do not use it when approved fields still contain the old prefix.

## Failures After the Save

A <Terminology title="The run stopped at a check or safety stage" to="/docs/reference/terminology#run-outcomes">Failure</Terminology> during the value checks or <Terminology title="Applies changed settings to a running service" to="/docs/reference/terminology#backups-and-service-reloads">service reloads</Terminology> that follow the save leaves the new values saved. Nothing is rolled back automatically, and the <Terminology title="The recorded starting prefix that changes are measured from" to="/docs/reference/terminology#baselines-and-transitions">baseline</Terminology> stays on the old prefix.

**<Terminology title="A copy of the config taken right before any write" to="/docs/reference/terminology#backups-and-service-reloads">Configuration Backup Created</Terminology>** shows Yes for these runs. [Backups and Recovery](/docs/operate/backups-and-recovery#after-a-failed-run) explains how to restore and retry or keep verified saved values with **Accept Current Prefix**.

## Notification Failures

If a <Terminology title="The alert sent after your addresses were updated" to="/docs/reference/terminology#notifications-and-logs">change notification</Terminology> can't be sent, the outcome is still <Terminology title="Prefix changed and every approved field was updated" to="/docs/reference/terminology#run-outcomes">Success</Terminology> and the <Terminology title="The recorded starting prefix that changes are measured from" to="/docs/reference/terminology#baselines-and-transitions">baseline</Terminology> still moves to the new prefix. The Status tab doesn't show delivery status, and the <Terminology title="pfSense's general log, where every run leaves lines" to="/docs/reference/terminology#notifications-and-logs">system log</Terminology> records `Configuration succeeded, but the change notification failed.`

Review [Status and Actions](/docs/operate/status-and-actions) for the fields behind each outcome and [How Updates Work](/docs/safety/how-updates-work) for the order of the stages.
