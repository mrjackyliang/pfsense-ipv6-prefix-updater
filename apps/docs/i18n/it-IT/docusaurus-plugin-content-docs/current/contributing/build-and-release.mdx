Controlla, prepara e impacchetta IPv6 Prefix Updater for pfSense, poi pubblica il pacchetto in una release GitHub.

## Requisiti \{#requirements}

- **Node.js 22, 24 o 26** — I manifest della radice e dei workspace accettano `^22 || ^24 || ^26`.
- **PHP o Docker** — Le suite PHP usano un `php` locale se presente, altrimenti l’immagine `php:8.3-cli-alpine` tramite Docker. `PHP_TEST_IMAGE` sostituisce l’immagine.
- **FreeBSD per il packaging** — `npm run deploy` funziona solo su FreeBSD, con `PFSENSE_PORTS_DIR` che punta a un checkout dei FreeBSD-ports di pfSense.

## Controlla, prepara e impacchetta \{#check-stage-and-package}

Esegui questi comandi dalla radice del repository:

```bash
# Lint and type-check the scripts, run the PHP and Vitest suites, and validate the port.
npm run check --workspace pfsense-pkg-ipv6-prefix-updater

# Copy the port into packages/ipv6-prefix-updater/build/port with the workspace version.
npm run build --workspace pfsense-pkg-ipv6-prefix-updater

# Build the package on FreeBSD into packages/ipv6-prefix-updater/build/release.
PFSENSE_PORTS_DIR=/path/to/FreeBSD-ports npm run deploy --workspace pfsense-pkg-ipv6-prefix-updater
```

- La preparazione trasforma `port/Makefile.template` in `build/port/Makefile` e vi imprime la `version` di `packages/ipv6-prefix-updater/package.json`.
- Il packaging copia il port preparato in `sysutils/pfSense-pkg-Ipv6PrefixUpdater` nel checkout dei ports, esegue `make package` e poi rimuove quella copia. Si ferma se la destinazione esiste già.
- `build/release` contiene quindi il `.pkg` con la versione, una copia chiamata `pfSense-pkg-Ipv6PrefixUpdater.pkg` e, per ciascuno, un file `.sha256` che contiene solo l’hash.

## Workflow di rilascio \{#release-workflow}

Il job `publish-pfsense-packages-ipv6-prefix-updater` in `.github/workflows/nova-publish-project.yml`, generato da Nova, viene eseguito nel workflow di pubblicazione:

1. Convalida e prepara il port su un runner Ubuntu.
2. Quando il secret `PFSENSE_RELEASE_SIGNING_KEY` è impostato, ricava la chiave pubblica da `PFSENSE_RELEASE_SIGNING_KEY` e la aggiunge al file `usr/local/share/pfSense-pkg-Ipv6PrefixUpdater/release-signing.pub` del port preparato.
3. Compila il pacchetto su FreeBSD con il checkout configurato dei FreeBSD-ports di pfSense.
4. Quando il secret è impostato, firma ogni `.pkg` come `<file>.pkg.sig` con `ssh-keygen -Y sign -n pfSense-pkg-Ipv6PrefixUpdater`.
5. Carica pacchetti, checksum e firme come artefatto del workflow conservato per 7 giorni e allega gli stessi file alla release.

La build contrassegna il pacchetto per qualsiasi versione di FreeBSD perché non contiene codice compilato, quindi un singolo pacchetto si installa su ogni release di pfSense supportata. `PFSENSE_FREEBSD_VERSION` seleziona solo la release di FreeBSD usata dalla VM di build. Il comando `pkg add` della guida di installazione scarica `pfSense-pkg-Ipv6PrefixUpdater.pkg` dalla release che GitHub contrassegna come più recente.

## Firma delle release \{#release-signing}

L’unica configurazione richiesta per la firma è il secret del repository `PFSENSE_RELEASE_SIGNING_KEY`, che contiene una chiave privata OpenSSH Ed25519 non cifrata.

1. In 1Password, scegli **New Item → SSH Key → Generate a New Key → Ed25519**.
2. Nel campo della chiave privata, scegli **Export**, seleziona il formato OpenSSH e non impostare una password.
3. Controlla gli appunti prima di salvare il secret:

   ```bash
   pbpaste | head -1
   ```

   Il comando deve mostrare `-----BEGIN OPENSSH PRIVATE KEY-----`.

4. Invia gli appunti direttamente a GitHub oppure leggi un file esportato:

   ```bash
   pbpaste | gh secret set PFSENSE_RELEASE_SIGNING_KEY
   gh secret set PFSENSE_RELEASE_SIGNING_KEY < <file>
   ```

5. Elimina il file della chiave privata esportata dopo aver salvato il secret.

Senza il secret, i pacchetti non includono una chiave pubblica e le release non sono firmate. Per cambiare chiave, aggiungi la nuova chiave pubblica `ssh-ed25519 ...` a `release-signing.pub`, pubblica una release mentre la vecchia chiave è ancora il secret, quindi sostituisci il secret con la nuova chiave.

Se la chiave di firma viene persa, le copie installate non possono autenticare una release firmata dalla chiave sostitutiva. Ogni installazione interessata deve usare una volta il comando manuale `pkg add -f` per installare un pacchetto che contiene la nuova chiave pubblica.

## Provare gli endpoint di aggiornamento in una VM \{#test-update-endpoints-in-a-vm}

La CLI accetta due variabili d’ambiente esclusivamente per test controllati in una VM:

- `IPV6_PREFIX_UPDATER_RELEASES_API` sostituisce l’URL dell’API dell’ultima release.
- `IPV6_PREFIX_UPDATER_DOWNLOAD_PREFIX` sostituisce il prefisso URL consentito per i file della release.

Vengono lette solo da `/usr/local/sbin/ipv6-prefix-updater`; non vengono mai salvate nella configurazione del pacchetto né lette direttamente dalla WebGUI. Imposta tutte le sostituzioni necessarie nella stessa invocazione della CLI:

```shell
IPV6_PREFIX_UPDATER_RELEASES_API=http://192.0.2.10/latest.json \
IPV6_PREFIX_UPDATER_DOWNLOAD_PREFIX=http://192.0.2.10/releases/ \
/usr/local/sbin/ipv6-prefix-updater --check-updates
```

Usa `--self-update` invece di `--check-updates` per provare l’intero percorso: download, checksum SHA-256, firma della release, metadati del pacchetto e `pkg add -f`.

## Suite di test PHP \{#php-test-suites}

- **`tests/domain.php`**: la <Terminology title="La scrittura breve in minuscolo, come 2001:db8::1" to="/docs/reference/terminology#addresses-and-prefixes">forma canonica</Terminology>, i limiti `/48` e `/64`, il mascheramento, i <Terminology title="I bit dopo il prefisso, sempre copiati invariati" to="/docs/reference/terminology#addresses-and-prefixes">bit host</Terminology> a `/53`, gli indirizzi rifiutati, la creazione di un piano senza effetti, il filtraggio per prefisso precedente e un cambio di lunghezza trattato come <Terminology title="Il prefisso è cambiato, quindi il pacchetto si mette al lavoro" to="/docs/reference/terminology#baselines-and-transitions">cambio di prefisso</Terminology>.
- **`tests/runtime.php`**: l’analisi di ogni <Terminology title="Un solo interruttore per un intero tipo di impostazione" to="/docs/reference/terminology#fields-and-change-plans">gruppo di campi</Terminology>, le eccezioni sui singoli campi, la nuova applicazione delle impostazioni degli altri pacchetti, lo <Terminology title="Il file con ogni linea di base, conservato anche dopo una reinstallazione" to="/docs/reference/terminology#running-checks">stato del pacchetto</Terminology> atomico, il <Terminology title="Impedisce che due controlli girino insieme" to="/docs/reference/terminology#running-checks">blocco di esecuzione</Terminology>, le piattaforme non supportate e i controlli pianificati disattivati. Copre anche l’ordine della transazione e gli errori di scrittura, backup, controllo preliminare dei ricaricamenti, ricaricamenti e notifica, oltre all’<Terminology title="Il prefisso è cambiato, ma nessun campo approvato usava il vecchio" to="/docs/reference/terminology#run-outcomes">Avviso</Terminology> senza corrispondenze.
- **`tests/pfsense-adapter.php`**: un aggiornamento forzato dell’indirizzo senza ripiego su <Terminology title="Un indirizzo fe80 che non viene mai usato come sorgente" to="/docs/reference/terminology#addresses-and-prefixes">link-local</Terminology>, il backup prima del salvataggio in sola scrittura e un backup non riuscito che si ferma prima della scrittura.
- **`tests/updates.php`**: confronto delle versioni, analisi delle release e convalida degli URL, pianificazioni casuali stabili, deduplicazione degli avvisi, digest dell’API GitHub, ripieghi `.sha256`, analisi delle chiavi di firma, output allowed-signers, argomenti esatti e standard input di `ssh-keygen`, firme valide, chiavi e namespace errati e pacchetti manomessi.
- **`tests/translations.php`** e **`tests/webgui-localization.php`**: cataloghi completi per ogni identificatore di lingua di pfSense, insieme al modulo Impostazioni e ai messaggi di convalida localizzati.

## Sito della documentazione \{#documentation-site}

Da `apps/docs`, `npm run check` esegue ESLint, il controllo dell’albero delle traduzioni, tre controlli dei tipi e le suite Vitest per i file `.env`, il frontmatter, i link, le tabelle, i link del glossario e le dichiarazioni dei tipi. `npm run build` compila tutte le lingue.

Le pagine della documentazione tradotte di ogni lingua si trovano in `apps/docs/i18n/<locale>/docusaurus-plugin-content-docs/current/` e rispecchiano le pagine in inglese, quindi aggiornale quando cambia una pagina in inglese. I testi dell’interfaccia (homepage, barra di navigazione, piè di pagina, blog ed etichette della barra laterale) provengono da `scripts/generate-locales.mjs`, che legge `scripts/locale-copies.json` e le traduzioni del pacchetto. `npm run i18n` esegue prima quel generatore, che lascia al loro posto le pagine della documentazione tradotte.

`.github/workflows/nova-publish-project.yml` compila il sito e lo pubblica su GitHub Pages quando viene pubblicata una release.
