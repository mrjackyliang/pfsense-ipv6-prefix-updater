## “当前状态”与“上次运行”的区别 \{#current-state-versus-last-run}

**当前状态** 只会在<Terminology title="初次检查：记录基线，不做任何改动" to="/docs/reference/terminology#run-outcomes">已初始化</Terminology>、**已接受** 和<Terminology title="前缀变了，所有已批准字段都已更新" to="/docs/reference/terminology#run-outcomes">成功</Terminology>时改变。失败的尝试永远不会成为下一次比较的依据，除非操作员事后核实已保存的值并明确接受当前活动前缀；**上次运行** 则记录表中任意结果的最近一次运行。

当另一个检查持有<Terminology title="确保两次检查不会同时运行" to="/docs/reference/terminology#running-checks">运行锁</Terminology>，或运行在读取<Terminology title="保存每条基线的文件，重装后依然保留" to="/docs/reference/terminology#running-checks">软件包状态</Terminology>之前就已停止（例如没有任何监控接口具有<Terminology title="位于 2000::/3 内的公网 IPv6 地址，唯一会用到的类型" to="/docs/reference/terminology#addresses-and-prefixes">全局地址</Terminology>）时，**上次运行** 保持不变。这些运行会把原因留在<Terminology title="最近一次运行的输出行，启动后立即显示" to="/docs/reference/terminology#running-checks">命令输出</Terminology>和<Terminology title="pfSense 的常规日志，每次运行都会留下记录" to="/docs/reference/terminology#notifications-and-logs">系统日志</Terminology>中。

## 警告：没有匹配的字段 \{#warning-no-matching-fields}

<Terminology title="前缀变了，但没有已批准字段使用旧前缀" to="/docs/reference/terminology#run-outcomes">警告</Terminology>表示前缀已变化，但没有任何<Terminology title="允许软件包改写的设置" to="/docs/reference/terminology#fields-and-change-plans">已批准字段</Terminology>属于旧前缀。不会写入任何内容，<Terminology title="记录下来的起始前缀，变化以它为准" to="/docs/reference/terminology#baselines-and-transitions">基线</Terminology>也停留在旧前缀上，因此下一次运行会再次检查同一<Terminology title="前缀变了，软件包开始工作" to="/docs/reference/terminology#baselines-and-transitions">前缀变化</Terminology>。

每次<Terminology title="前缀变了，但没有已批准字段使用旧前缀" to="/docs/reference/terminology#run-outcomes">警告</Terminology>都会添加一条 <Terminology title="pfSense 自带通知列表中的提醒" to="/docs/reference/terminology#notifications-and-logs">WebGUI 通知</Terminology>，<Terminology title="预览改动，但不写入任何内容" to="/docs/reference/terminology#running-checks">试运行</Terminology>产生的警告也不例外。如果原因未解决，每次计划运行都会再添加一条新通知。

常见原因：

- 包含这些地址的<Terminology title="一个开关管住一整类设置" to="/docs/reference/terminology#fields-and-change-plans">字段组</Terminology>已关闭，或相应字段已被取消勾选。
- 这些地址已在软件包之外被更改。
- 这些地址位于[其他设置](/docs/configure/configuration-scopes#other-settings)组中，该组在你勾选这些地址之前保持关闭。
- 之前的一次<Terminology title="运行在某个检查或安全阶段停止" to="/docs/reference/terminology#run-outcomes">失败</Terminology>已保存新值，但保留了旧<Terminology title="记录下来的起始前缀，变化以它为准" to="/docs/reference/terminology#baselines-and-transitions">基线</Terminology>。
- <Terminology title="ISP 前缀的大小，例如 /56，由你设置" to="/docs/reference/terminology#addresses-and-prefixes">委派前缀长度</Terminology>被[改得更短](/docs/configure/interface-and-prefix#changing-the-prefix-length)（网络变宽），而前缀本身并未变化。

[故障排除](/docs/operate/troubleshooting#warning-on-every-run)逐一介绍了这些原因。

如果这些地址已被正确更改，请在核实已保存的地址和受影响的服务后，使用 **状态 → 操作 → 基线恢复 → 接受当前前缀**。这会记录一个 **已接受** 结果，既不扫描已批准字段，也不更改防火墙配置；如果已批准字段中仍包含旧前缀，请不要使用它。

## 保存后的失败 \{#failures-after-the-save}

如果在保存之后的值检查或<Terminology title="将更改后的设置应用到正在运行的服务" to="/docs/reference/terminology#backups-and-service-reloads">服务重新加载</Terminology>中发生<Terminology title="运行在某个检查或安全阶段停止" to="/docs/reference/terminology#run-outcomes">失败</Terminology>，新值仍会保持已保存状态。系统不会自动回滚任何内容，<Terminology title="记录下来的起始前缀，变化以它为准" to="/docs/reference/terminology#baselines-and-transitions">基线</Terminology>也停留在旧前缀上。

这类运行的 **<Terminology title="每次写入前一刻保存的配置副本" to="/docs/reference/terminology#backups-and-service-reloads">已创建配置备份</Terminology>** 显示“是”。[备份与恢复](/docs/operate/backups-and-recovery#after-a-failed-run)说明了如何恢复后重试，或通过 **接受当前前缀** 保留已核实的已保存值。

## 通知失败 \{#notification-failures}

如果<Terminology title="地址更新后发送的通知" to="/docs/reference/terminology#notifications-and-logs">变化通知</Terminology>无法发送，结果仍为<Terminology title="前缀变了，所有已批准字段都已更新" to="/docs/reference/terminology#run-outcomes">成功</Terminology>，<Terminology title="记录下来的起始前缀，变化以它为准" to="/docs/reference/terminology#baselines-and-transitions">基线</Terminology>也照样移到新前缀。“状态”选项卡不显示发送状态，<Terminology title="pfSense 的常规日志，每次运行都会留下记录" to="/docs/reference/terminology#notifications-and-logs">系统日志</Terminology>会记录 `配置已成功更新，但变化通知发送失败。`

每种结果对应的字段请参阅[状态与操作](/docs/operate/status-and-actions)，各阶段的顺序请参阅[更新工作原理](/docs/safety/how-updates-work)。
