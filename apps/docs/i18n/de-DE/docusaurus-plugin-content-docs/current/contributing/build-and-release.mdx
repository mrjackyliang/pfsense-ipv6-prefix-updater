Prüfen Sie IPv6 Prefix Updater for pfSense, stellen Sie es bereit und paketieren Sie es, und veröffentlichen Sie das Paket dann in einem GitHub-Release.

## Voraussetzungen \{#requirements}

- **Node.js 22, 24 oder 26** — Die Manifeste im Root und in den Workspaces akzeptieren `^22 || ^24 || ^26`.
- **PHP oder Docker** — Die PHP-Suiten verwenden ein lokales `php`, wenn vorhanden, sonst über Docker das Image `php:8.3-cli-alpine`. `PHP_TEST_IMAGE` überschreibt das Image.
- **FreeBSD zum Paketieren** — `npm run deploy` läuft nur unter FreeBSD, wobei `PFSENSE_PORTS_DIR` auf einen Checkout der FreeBSD-ports von pfSense zeigt.

## Prüfen, bereitstellen und paketieren \{#check-stage-and-package}

Führen Sie diese Befehle im Stammverzeichnis des Repositorys aus:

```bash
# Lint and type-check the scripts, run the PHP and Vitest suites, and validate the port.
npm run check --workspace pfsense-pkg-ipv6-prefix-updater

# Copy the port into packages/ipv6-prefix-updater/build/port with the workspace version.
npm run build --workspace pfsense-pkg-ipv6-prefix-updater

# Build the package on FreeBSD into packages/ipv6-prefix-updater/build/release.
PFSENSE_PORTS_DIR=/path/to/FreeBSD-ports npm run deploy --workspace pfsense-pkg-ipv6-prefix-updater
```

- Das Bereitstellen macht aus `port/Makefile.template` die Datei `build/port/Makefile` und versieht sie mit der `version` aus `packages/ipv6-prefix-updater/package.json`.
- Das Paketieren kopiert den bereitgestellten Port nach `sysutils/pfSense-pkg-Ipv6PrefixUpdater` im Ports-Checkout, führt `make package` aus und entfernt diese Kopie wieder. Es stoppt, wenn das Ziel bereits existiert.
- `build/release` enthält danach das versionierte `.pkg`, eine Kopie namens `pfSense-pkg-Ipv6PrefixUpdater.pkg` und zu jeder Datei eine `.sha256`-Datei, die nur den Hash enthält.

## Release-Workflow \{#release-workflow}

Der von Nova erzeugte Job `publish-pfsense-packages-ipv6-prefix-updater` in `.github/workflows/nova-publish-project.yml` läuft im Publish-Workflow:

1. Validiert den Port und stellt ihn auf einem Ubuntu-Runner bereit.
2. Leitet, wenn das Secret `PFSENSE_RELEASE_SIGNING_KEY` gesetzt ist, den öffentlichen Schlüssel aus `PFSENSE_RELEASE_SIGNING_KEY` ab und hängt ihn an `usr/local/share/pfSense-pkg-Ipv6PrefixUpdater/release-signing.pub` im bereitgestellten Port an.
3. Baut das Paket unter FreeBSD mit dem konfigurierten Checkout der pfSense-FreeBSD-ports.
4. Signiert, wenn das Secret gesetzt ist, jede `.pkg`-Datei als `<file>.pkg.sig` mit `ssh-keygen -Y sign -n pfSense-pkg-Ipv6PrefixUpdater`.
5. Lädt Pakete, Prüfsummen und Signaturen als Workflow-Artefakt mit 7 Tagen Aufbewahrung hoch und hängt dieselben Dateien an das Release an.

Der Build kennzeichnet das Paket für jede FreeBSD-Version, da es keinen kompilierten Code enthält. Dadurch lässt sich ein einziges Paket auf jedem unterstützten pfSense-Release installieren. `PFSENSE_FREEBSD_VERSION` wählt nur das FreeBSD-Release der Build-VM aus. Der `pkg add`-Befehl der Installationsanleitung lädt `pfSense-pkg-Ipv6PrefixUpdater.pkg` aus dem Release, das GitHub als neuestes markiert.

## Release-Signierung \{#release-signing}

Die einzige Einrichtung für die Signierung ist das Repository-Secret `PFSENSE_RELEASE_SIGNING_KEY` mit einem unverschlüsselten privaten OpenSSH-Ed25519-Schlüssel.

1. Wählen Sie in 1Password **New Item → SSH Key → Generate a New Key → Ed25519**.
2. Wählen Sie im Feld für den privaten Schlüssel **Export**, das OpenSSH-Format und kein Passwort.
3. Prüfen Sie die Zwischenablage, bevor Sie das Secret speichern:

   ```bash
   pbpaste | head -1
   ```

   Der Befehl muss `-----BEGIN OPENSSH PRIVATE KEY-----` ausgeben.

4. Senden Sie die Zwischenablage direkt an GitHub oder lesen Sie eine exportierte Datei ein:

   ```bash
   pbpaste | gh secret set PFSENSE_RELEASE_SIGNING_KEY
   gh secret set PFSENSE_RELEASE_SIGNING_KEY < <file>
   ```

5. Löschen Sie die exportierte Datei mit dem privaten Schlüssel, nachdem das Secret gespeichert wurde.

Ohne das Secret enthalten Pakete keinen öffentlichen Schlüssel und Releases sind unsigniert. Fügen Sie für einen Schlüsselwechsel den neuen öffentlichen Schlüssel `ssh-ed25519 ...` zu `release-signing.pub` hinzu, veröffentlichen Sie ein Release, solange der alte Schlüssel noch das Secret ist, und ersetzen Sie das Secret danach durch den neuen Schlüssel.

Geht der Signierschlüssel verloren, können installierte Kopien ein mit seinem Ersatz signiertes Release nicht authentifizieren. Jede betroffene Installation muss einmal den manuellen Befehl `pkg add -f` verwenden, um ein Paket mit dem neuen öffentlichen Schlüssel zu installieren.

## Aktualisierungsziele in einer VM testen \{#test-update-endpoints-in-a-vm}

Die CLI akzeptiert zwei Umgebungsvariablen ausschließlich für kontrollierte VM-Tests:

- `IPV6_PREFIX_UPDATER_RELEASES_API` ersetzt die API-URL für das neueste Release.
- `IPV6_PREFIX_UPDATER_DOWNLOAD_PREFIX` ersetzt das erlaubte URL-Präfix für Assets.

Sie werden nur von `/usr/local/sbin/ipv6-prefix-updater` gelesen; sie werden nie in der Paketkonfiguration gespeichert oder direkt von der WebGUI gelesen. Setzen Sie alle benötigten Überschreibungen im selben CLI-Aufruf:

```shell
IPV6_PREFIX_UPDATER_RELEASES_API=http://192.0.2.10/latest.json \
IPV6_PREFIX_UPDATER_DOWNLOAD_PREFIX=http://192.0.2.10/releases/ \
/usr/local/sbin/ipv6-prefix-updater --check-updates
```

Verwenden Sie `--self-update` statt `--check-updates`, um den vollständigen Pfad aus Download, SHA-256-Prüfsumme, Release-Signatur, Paketmetadaten und `pkg add -f` zu testen.

## PHP-Testsuiten \{#php-test-suites}

- **`tests/domain.php`**: <Terminology title="Die kurze Kleinschreibung, etwa 2001:db8::1" to="/docs/reference/terminology#addresses-and-prefixes">kanonische Form</Terminology>, die Grenzen `/48` und `/64`, Maskierung, <Terminology title="Die Bits nach dem Präfix, immer unverändert übernommen" to="/docs/reference/terminology#addresses-and-prefixes">Hostbits</Terminology> bei `/53`, abgelehnte Adressen, No-op-Planung, Filterung nach vorherigem Präfix und eine Längenänderung, die als <Terminology title="Ihr Präfix hat sich geändert, also legt das Paket los" to="/docs/reference/terminology#baselines-and-transitions">Präfixwechsel</Terminology> behandelt wird.
- **`tests/runtime.php`**: das Durchsuchen jeder <Terminology title="Ein Schalter für eine ganze Art von Einstellung" to="/docs/reference/terminology#fields-and-change-plans">Feldgruppe</Terminology>, Ausnahmen für einzelne Felder, das erneute Anwenden der Einstellungen anderer Pakete, atomarer <Terminology title="Die Datei mit jeder Basislinie, bleibt bei Neuinstallation erhalten" to="/docs/reference/terminology#running-checks">Paketzustand</Terminology>, die <Terminology title="Verhindert, dass zwei Prüfungen gleichzeitig laufen" to="/docs/reference/terminology#running-checks">Laufsperre</Terminology>, nicht unterstützte Plattformen und deaktivierte geplante Prüfungen. Abgedeckt sind auch die Transaktionsreihenfolge und Fehler beim Schreiben, bei der Sicherung, bei der Vorabprüfung des Neuladens, beim Neuladen und bei der Benachrichtigung sowie die <Terminology title="Präfix geändert, aber kein genehmigtes Feld nutzte das alte" to="/docs/reference/terminology#run-outcomes">Warnung</Terminology> ohne Treffer.
- **`tests/pfsense-adapter.php`**: eine erzwungene Adressaktualisierung ohne <Terminology title="Eine fe80-Adresse, die nie als Quelle dient" to="/docs/reference/terminology#addresses-and-prefixes">Link-Local</Terminology>-Rückgriff, die Sicherung vor dem reinen Schreibvorgang und eine fehlgeschlagene Sicherung, die vor dem Schreiben stoppt.
- **`tests/updates.php`**: Versionsvergleich, Release-Verarbeitung und URL-Prüfung, stabile zufällige Zeitpläne, Deduplizierung von Hinweisen, GitHub-API-Digests, `.sha256`-Fallbacks, Verarbeitung von Signierschlüsseln, Allowed-Signers-Ausgabe, exakte `ssh-keygen`-Argumente und Standardeingabe, gültige Signaturen, falsche Schlüssel und Namespaces sowie manipulierte Pakete.
- **`tests/translations.php`** und **`tests/webgui-localization.php`**: vollständige Kataloge für jede pfSense-Sprachkennung sowie das lokalisierte Einstellungsformular und seine Validierungsmeldungen.

## Dokumentationssite \{#documentation-site}

In `apps/docs` führt `npm run check` ESLint, die Prüfung des Übersetzungsbaums, drei Typprüfungen und die Vitest-Suiten für `.env`-Dateien, Frontmatter, Links, Tabellen, Glossarlinks und Typdeklarationen aus. `npm run build` baut jede Locale.

Die übersetzten Docs-Seiten jeder Locale liegen in `apps/docs/i18n/<locale>/docusaurus-plugin-content-docs/current/` und spiegeln die englischen Seiten wider. Aktualisieren Sie sie daher, wenn sich eine englische Seite ändert. Die Oberflächentexte (Startseite, Navigationsleiste, Fußzeile, Blog und Seitenleisten-Beschriftungen) stammen aus `scripts/generate-locales.mjs`, das `scripts/locale-copies.json` und die Paketübersetzungen liest. `npm run i18n` führt diesen Generator zuerst aus und lässt die übersetzten Docs-Seiten unverändert.

`.github/workflows/nova-publish-project.yml` baut die Site und stellt sie auf GitHub Pages bereit, wenn ein Release veröffentlicht wird.
