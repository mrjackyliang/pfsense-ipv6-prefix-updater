Vérifiez, préparez et empaquetez IPv6 Prefix Updater for pfSense, puis publiez le paquet dans une version GitHub.

## Prérequis \{#requirements}

- **Node.js 22, 24 ou 26** — Les manifestes racine et d’espace de travail acceptent `^22 || ^24 || ^26`.
- **PHP ou Docker** — Les suites PHP utilisent un `php` local s’il existe, ou l’image `php:8.3-cli-alpine` via Docker. `PHP_TEST_IMAGE` remplace l’image.
- **FreeBSD pour l’empaquetage** — `npm run deploy` ne s’exécute que sur FreeBSD, avec `PFSENSE_PORTS_DIR` pointant vers une copie de travail des ports FreeBSD de pfSense.

## Vérifier, préparer et empaqueter \{#check-stage-and-package}

Exécutez ces commandes depuis la racine du dépôt :

```bash
# Lint and type-check the scripts, run the PHP and Vitest suites, and validate the port.
npm run check --workspace pfsense-pkg-ipv6-prefix-updater

# Copy the port into packages/ipv6-prefix-updater/build/port with the workspace version.
npm run build --workspace pfsense-pkg-ipv6-prefix-updater

# Build the package on FreeBSD into packages/ipv6-prefix-updater/build/release.
PFSENSE_PORTS_DIR=/path/to/FreeBSD-ports npm run deploy --workspace pfsense-pkg-ipv6-prefix-updater
```

- La préparation transforme `port/Makefile.template` en `build/port/Makefile` et y inscrit la `version` de `packages/ipv6-prefix-updater/package.json`.
- L’empaquetage copie le port préparé vers `sysutils/pfSense-pkg-Ipv6PrefixUpdater` dans la copie des ports, lance `make package`, puis supprime cette copie. Il s’arrête si la destination existe déjà.
- `build/release` contient alors le `.pkg` versionné, une copie nommée `pfSense-pkg-Ipv6PrefixUpdater.pkg` et, pour chacun, un fichier `.sha256` qui ne contient que l’empreinte.

## Workflow de publication \{#release-workflow}

Le job `publish-pfsense-packages-ipv6-prefix-updater` de `.github/workflows/nova-publish-project.yml`, généré par Nova, s’exécute dans le workflow de publication :

1. Valide et prépare le port sur un runner Ubuntu.
2. Lorsque le secret `PFSENSE_RELEASE_SIGNING_KEY` est défini, dérive la clé publique de `PFSENSE_RELEASE_SIGNING_KEY` et l’ajoute au fichier `usr/local/share/pfSense-pkg-Ipv6PrefixUpdater/release-signing.pub` du port préparé.
3. Compile le paquet sur FreeBSD avec la copie configurée des FreeBSD-ports de pfSense.
4. Lorsque le secret est défini, signe chaque `.pkg` sous la forme `<file>.pkg.sig` avec `ssh-keygen -Y sign -n pfSense-pkg-Ipv6PrefixUpdater`.
5. Téléverse les paquets, sommes et signatures comme artefact de workflow conservé 7 jours et joint les mêmes fichiers à la version.

La compilation marque le paquet pour toute version de FreeBSD, car il ne contient aucun code compilé. Un seul paquet s’installe ainsi sur chaque version de pfSense prise en charge. `PFSENSE_FREEBSD_VERSION` sélectionne uniquement la version de FreeBSD utilisée par la machine virtuelle de compilation. La commande `pkg add` du guide d’installation récupère `pfSense-pkg-Ipv6PrefixUpdater.pkg` dans la version que GitHub marque comme la plus récente.

## Signature des versions \{#release-signing}

La seule configuration requise pour la signature est le secret de dépôt `PFSENSE_RELEASE_SIGNING_KEY`, qui contient une clé privée OpenSSH Ed25519 non chiffrée.

1. Dans 1Password, choisissez **New Item → SSH Key → Generate a New Key → Ed25519**.
2. Dans le champ de la clé privée, choisissez **Export**, sélectionnez le format OpenSSH et ne définissez aucun mot de passe.
3. Vérifiez le presse-papiers avant d’enregistrer le secret :

   ```bash
   pbpaste | head -1
   ```

   La commande doit afficher `-----BEGIN OPENSSH PRIVATE KEY-----`.

4. Envoyez directement le presse-papiers à GitHub ou lisez un fichier exporté :

   ```bash
   pbpaste | gh secret set PFSENSE_RELEASE_SIGNING_KEY
   gh secret set PFSENSE_RELEASE_SIGNING_KEY < <file>
   ```

5. Supprimez le fichier de clé privée exporté une fois le secret enregistré.

Sans ce secret, les paquets ne contiennent aucune clé publique et les versions ne sont pas signées. Pour changer de clé, ajoutez la nouvelle clé publique `ssh-ed25519 ...` à `release-signing.pub`, publiez une version tant que l’ancienne clé est encore le secret, puis remplacez le secret par la nouvelle clé.

Si la clé de signature est perdue, les copies installées ne peuvent pas authentifier une version signée par sa remplaçante. Chaque installation concernée doit utiliser une fois la commande manuelle `pkg add -f` pour installer un paquet contenant la nouvelle clé publique.

## Tester les points de terminaison dans une VM \{#test-update-endpoints-in-a-vm}

La CLI accepte deux variables d’environnement, uniquement pour des tests contrôlés dans une VM :

- `IPV6_PREFIX_UPDATER_RELEASES_API` remplace l’URL de l’API de la dernière version.
- `IPV6_PREFIX_UPDATER_DOWNLOAD_PREFIX` remplace le préfixe d’URL autorisé pour les fichiers de version.

Elles ne sont lues que par `/usr/local/sbin/ipv6-prefix-updater` ; elles ne sont jamais enregistrées dans la configuration du paquet ni lues directement par le WebGUI. Définissez toutes les substitutions nécessaires dans le même appel de la CLI :

```shell
IPV6_PREFIX_UPDATER_RELEASES_API=http://192.0.2.10/latest.json \
IPV6_PREFIX_UPDATER_DOWNLOAD_PREFIX=http://192.0.2.10/releases/ \
/usr/local/sbin/ipv6-prefix-updater --check-updates
```

Utilisez `--self-update` à la place de `--check-updates` pour tester tout le parcours : téléchargement, somme SHA-256, signature de version, métadonnées du paquet et `pkg add -f`.

## Suites de tests PHP \{#php-test-suites}

- **`tests/domain.php`** : la <Terminology title="L’écriture courte en minuscules, comme 2001:db8::1" to="/docs/reference/terminology#addresses-and-prefixes">forme canonique</Terminology>, les bornes `/48` et `/64`, le masquage, les <Terminology title="Les bits après le préfixe, toujours recopiés tels quels" to="/docs/reference/terminology#addresses-and-prefixes">bits d’hôte</Terminology> à `/53`, les adresses refusées, l’établissement d’un plan sans effet, le filtrage par préfixe précédent et un changement de longueur traité comme un <Terminology title="Votre préfixe a changé, le paquet se met donc au travail" to="/docs/reference/terminology#baselines-and-transitions">changement de préfixe</Terminology>.
- **`tests/runtime.php`** : l’analyse de chaque <Terminology title="Un seul interrupteur pour tout un type de réglage" to="/docs/reference/terminology#fields-and-change-plans">groupe de champs</Terminology>, les exceptions portant sur un seul champ, la nouvelle application des paramètres des autres paquets, l’<Terminology title="Le fichier qui garde chaque référence, même après réinstallation" to="/docs/reference/terminology#running-checks">état du paquet</Terminology> atomique, le <Terminology title="Empêche deux vérifications de tourner en même temps" to="/docs/reference/terminology#running-checks">verrou d’exécution</Terminology>, les plateformes non prises en charge et les vérifications planifiées désactivées. Elle couvre aussi l’ordre de la transaction et les échecs de l’écriture, de la sauvegarde, du contrôle préalable des rechargements, des rechargements et de la notification, ainsi que l’<Terminology title="Le préfixe a changé, mais aucun champ approuvé n’utilisait l’ancien" to="/docs/reference/terminology#run-outcomes">Avertissement</Terminology> sans correspondance.
- **`tests/pfsense-adapter.php`** : une actualisation forcée de l’adresse sans repli <Terminology title="Une adresse fe80 qui ne sert jamais de source" to="/docs/reference/terminology#addresses-and-prefixes">lien-local</Terminology>, la sauvegarde avant l’enregistrement en écriture seule et une sauvegarde échouée qui s’arrête avant l’écriture.
- **`tests/updates.php`** : comparaison des versions, analyse des versions et validation des URL, planifications aléatoires stables, déduplication des notifications, empreintes de l’API GitHub, solutions de repli `.sha256`, analyse des clés de signature, sortie allowed-signers, arguments exacts et entrée standard de `ssh-keygen`, signatures valides, mauvaises clés et espaces de noms, et paquets altérés.
- **`tests/translations.php`** et **`tests/webgui-localization.php`** : des catalogues complets pour chaque identifiant de langue pfSense, ainsi que le formulaire Paramètres et les messages de validation traduits.

## Site de documentation \{#documentation-site}

Depuis `apps/docs`, `npm run check` lance ESLint, la vérification de l’arborescence des traductions, trois vérifications de types et les suites Vitest pour les fichiers `.env`, le frontmatter, les liens, les tableaux, les liens du glossaire et les déclarations de types. `npm run build` compile toutes les langues.

Les pages de documentation traduites de chaque langue se trouvent dans `apps/docs/i18n/<locale>/docusaurus-plugin-content-docs/current/` et reprennent les pages anglaises ; mettez-les donc à jour dès qu’une page anglaise change. Les textes de l’interface (page d’accueil, barre de navigation, pied de page, blog et libellés de la barre latérale) proviennent de `scripts/generate-locales.mjs`, qui lit `scripts/locale-copies.json` et les traductions du paquet. `npm run i18n` lance d’abord ce générateur, qui laisse en place les pages de documentation traduites.

`.github/workflows/nova-publish-project.yml` compile le site et le déploie sur GitHub Pages quand une version est publiée.
