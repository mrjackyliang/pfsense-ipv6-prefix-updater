Sprawdź, przygotuj i spakuj IPv6 Prefix Updater for pfSense, a następnie opublikuj pakiet w wydaniu w serwisie GitHub.

## Wymagania \{#requirements}

- **Node.js 22, 24 lub 26** — manifesty główny i obszaru roboczego akceptują `^22 || ^24 || ^26`.
- **PHP lub Docker** — zestawy testów PHP używają lokalnego `php`, jeśli jest dostępny, albo obrazu `php:8.3-cli-alpine` przez Docker. `PHP_TEST_IMAGE` zastępuje ten obraz.
- **FreeBSD do pakowania** — `npm run deploy` działa tylko w systemie FreeBSD, gdy `PFSENSE_PORTS_DIR` wskazuje na kopię roboczą FreeBSD-ports z pfSense.

## Sprawdzanie, przygotowanie i pakowanie \{#check-stage-and-package}

Uruchom te polecenia w katalogu głównym repozytorium:

```bash
# Lint and type-check the scripts, run the PHP and Vitest suites, and validate the port.
npm run check --workspace pfsense-pkg-ipv6-prefix-updater

# Copy the port into packages/ipv6-prefix-updater/build/port with the workspace version.
npm run build --workspace pfsense-pkg-ipv6-prefix-updater

# Build the package on FreeBSD into packages/ipv6-prefix-updater/build/release.
PFSENSE_PORTS_DIR=/path/to/FreeBSD-ports npm run deploy --workspace pfsense-pkg-ipv6-prefix-updater
```

- Przygotowanie przekształca `port/Makefile.template` w `build/port/Makefile` i oznacza go wartością `version` z `packages/ipv6-prefix-updater/package.json`.
- Pakowanie kopiuje przygotowany port do `sysutils/pfSense-pkg-Ipv6PrefixUpdater` w kopii roboczej portów, uruchamia `make package` i ponownie usuwa tę kopię. Zatrzymuje się, jeśli miejsce docelowe już istnieje.
- Następnie `build/release` zawiera plik `.pkg` z numerem wersji, kopię o nazwie `pfSense-pkg-Ipv6PrefixUpdater.pkg` oraz dla każdego z nich plik `.sha256`, który zawiera tylko skrót.

## Przepływ pracy wydania \{#release-workflow}

Zadanie `publish-pfsense-packages-ipv6-prefix-updater` w pliku `.github/workflows/nova-publish-project.yml`, generowanym przez Nova, jest uruchamiane w przepływie publikacji:

1. Weryfikuje i przygotowuje port na runnerze Ubuntu.
2. Gdy ustawiony jest sekret `PFSENSE_RELEASE_SIGNING_KEY`, wyprowadza klucz publiczny z `PFSENSE_RELEASE_SIGNING_KEY` i dopisuje go do `usr/local/share/pfSense-pkg-Ipv6PrefixUpdater/release-signing.pub` w przygotowanym porcie.
3. Buduje pakiet we FreeBSD przy użyciu skonfigurowanej kopii repozytorium FreeBSD-ports pfSense.
4. Gdy sekret jest ustawiony, podpisuje każdy plik `.pkg` jako `<file>.pkg.sig` poleceniem `ssh-keygen -Y sign -n pfSense-pkg-Ipv6PrefixUpdater`.
5. Przesyła pakiety, sumy kontrolne i podpisy jako artefakt przepływu przechowywany przez 7 dni oraz dołącza te same pliki do wydania.

Kompilacja oznacza pakiet jako przeznaczony dla każdej wersji FreeBSD, ponieważ nie zawiera on skompilowanego kodu. Dzięki temu jeden pakiet można zainstalować w każdym obsługiwanym wydaniu pfSense. `PFSENSE_FREEBSD_VERSION` wybiera jedynie wydanie FreeBSD używane przez maszynę wirtualną kompilacji. Polecenie `pkg add` z przewodnika instalacji pobiera `pfSense-pkg-Ipv6PrefixUpdater.pkg` z wydania, które GitHub oznacza jako najnowsze.

## Podpisywanie wydań \{#release-signing}

Jedyną konfiguracją podpisywania jest sekret repozytorium `PFSENSE_RELEASE_SIGNING_KEY` zawierający niezaszyfrowany klucz prywatny OpenSSH Ed25519.

1. W 1Password wybierz **New Item → SSH Key → Generate a New Key → Ed25519**.
2. W polu klucza prywatnego wybierz **Export**, format OpenSSH i nie ustawiaj hasła.
3. Sprawdź schowek przed zapisaniem sekretu:

   ```bash
   pbpaste | head -1
   ```

   Polecenie powinno wyświetlić `-----BEGIN OPENSSH PRIVATE KEY-----`.

4. Wyślij schowek bezpośrednio do GitHub albo odczytaj wyeksportowany plik:

   ```bash
   pbpaste | gh secret set PFSENSE_RELEASE_SIGNING_KEY
   gh secret set PFSENSE_RELEASE_SIGNING_KEY < <file>
   ```

5. Po zapisaniu sekretu usuń wyeksportowany plik klucza prywatnego.

Bez sekretu pakiety nie zawierają klucza publicznego, a wydania nie są podpisane. Aby zmienić klucz, dodaj nowy klucz publiczny `ssh-ed25519 ...` do `release-signing.pub`, opublikuj jedno wydanie, gdy stary klucz nadal jest sekretem, a następnie zastąp sekret nowym kluczem.

Jeśli klucz podpisujący zostanie utracony, zainstalowane kopie nie mogą uwierzytelnić wydania podpisanego kluczem zastępczym. Każda taka instalacja musi raz użyć ręcznego polecenia `pkg add -f`, aby zainstalować pakiet z nowym kluczem publicznym.

## Testowanie punktów aktualizacji w maszynie wirtualnej \{#test-update-endpoints-in-a-vm}

CLI przyjmuje dwie zmienne środowiskowe wyłącznie na potrzeby kontrolowanych testów w maszynie wirtualnej:

- `IPV6_PREFIX_UPDATER_RELEASES_API` zastępuje adres URL API najnowszego wydania.
- `IPV6_PREFIX_UPDATER_DOWNLOAD_PREFIX` zastępuje dozwolony prefiks adresu URL zasobu.

Odczytuje je tylko `/usr/local/sbin/ipv6-prefix-updater`; nigdy nie są zapisywane w konfiguracji pakietu ani odczytywane bezpośrednio przez WebGUI. Ustaw wszystkie potrzebne zastąpienia w tym samym wywołaniu CLI:

```shell
IPV6_PREFIX_UPDATER_RELEASES_API=http://192.0.2.10/latest.json \
IPV6_PREFIX_UPDATER_DOWNLOAD_PREFIX=http://192.0.2.10/releases/ \
/usr/local/sbin/ipv6-prefix-updater --check-updates
```

Użyj `--self-update` zamiast `--check-updates`, aby przetestować całą ścieżkę pobierania, sumy SHA-256, podpisu wydania, metadanych pakietu i `pkg add -f`.

## Zestawy testów PHP \{#php-test-suites}

- **`tests/domain.php`**: <Terminology title="Krótki zapis małymi literami, np. 2001:db8::1" to="/docs/reference/terminology#addresses-and-prefixes">postać kanoniczna</Terminology>, granice `/48` i `/64`, maskowanie, <Terminology title="Bity po prefiksie, zawsze kopiowane bez zmian" to="/docs/reference/terminology#addresses-and-prefixes">bity hosta</Terminology> przy `/53`, odrzucane adresy, planowanie bez zmian, filtrowanie według poprzedniego prefiksu oraz zmiana długości traktowana jako <Terminology title="Twój prefiks się zmienił, więc pakiet bierze się do pracy" to="/docs/reference/terminology#baselines-and-transitions">zmiana prefiksu</Terminology>.
- **`tests/runtime.php`**: skanowanie każdej <Terminology title="Jeden przełącznik dla całego rodzaju ustawień" to="/docs/reference/terminology#fields-and-change-plans">grupy pól</Terminology>, wyjątki dla pojedynczych pól, ponowne stosowanie ustawień innych pakietów, atomowy <Terminology title="Plik z każdą wartością bazową, zachowany po ponownej instalacji" to="/docs/reference/terminology#running-checks">stan pakietu</Terminology>, <Terminology title="Nie pozwala, by dwa sprawdzenia działały jednocześnie" to="/docs/reference/terminology#running-checks">blokada uruchomienia</Terminology>, nieobsługiwane platformy i wyłączone zaplanowane sprawdzenia. Obejmuje też kolejność transakcji i błędy zapisu, kopii zapasowej, kontroli wstępnej ponownego załadowania, ponownego załadowania i powiadomienia, a także <Terminology title="Prefiks się zmienił, ale żadne zatwierdzone pole nie używało starego" to="/docs/reference/terminology#run-outcomes">Ostrzeżenie</Terminology> przy zerowej liczbie dopasowań.
- **`tests/pfsense-adapter.php`**: wymuszone odświeżenie adresu bez zastępczego użycia adresu <Terminology title="Adres fe80, który nigdy nie służy jako źródło" to="/docs/reference/terminology#addresses-and-prefixes">link-local</Terminology>, kopia zapasowa przed samym zapisem (write-only) oraz nieudana kopia zapasowa, która zatrzymuje uruchomienie przed zapisem.
- **`tests/updates.php`**: porównywanie wersji, przetwarzanie wydań i sprawdzanie adresów URL, stabilne losowe harmonogramy, deduplikacja powiadomień, skróty z interfejsu GitHub API, pliki zastępcze `.sha256`, przetwarzanie kluczy podpisujących, wynik allowed-signers, dokładne argumenty i standardowe wejście `ssh-keygen`, poprawne podpisy, błędne klucze i przestrzenie nazw oraz zmodyfikowane pakiety.
- **`tests/translations.php`** i **`tests/webgui-localization.php`**: kompletne katalogi dla każdego identyfikatora języka pfSense oraz zlokalizowany formularz Ustawienia i komunikaty walidacji.

## Witryna dokumentacji \{#documentation-site}

W katalogu `apps/docs` polecenie `npm run check` uruchamia ESLint, kontrolę drzewa tłumaczeń, trzy kontrole typów oraz zestawy Vitest dla plików `.env`, frontmattera, linków, tabel, linków do słowniczka i deklaracji typów. `npm run build` buduje wszystkie wersje językowe.

Przetłumaczone strony dokumentacji każdej wersji językowej znajdują się w `apps/docs/i18n/<locale>/docusaurus-plugin-content-docs/current/` i odpowiadają stronom angielskim, dlatego zaleca się aktualizować je przy każdej zmianie strony angielskiej. Teksty interfejsu (strona główna, pasek nawigacji, stopka, blog i etykiety paska bocznego) pochodzą ze skryptu `scripts/generate-locales.mjs`, który odczytuje `scripts/locale-copies.json` i tłumaczenia pakietu. `npm run i18n` najpierw uruchamia ten generator, który pozostawia przetłumaczone strony dokumentacji bez zmian.

`.github/workflows/nova-publish-project.yml` buduje witrynę i wdraża ją w GitHub Pages po opublikowaniu wydania.
