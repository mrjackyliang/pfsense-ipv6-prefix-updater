Verifique, prepare e empacote o IPv6 Prefix Updater for pfSense e depois publique o pacote em uma release do GitHub.

## Requisitos \{#requirements}

- **Node.js 22, 24 ou 26** — Os manifestos da raiz e do workspace aceitam `^22 || ^24 || ^26`.
- **PHP ou Docker** — As suítes PHP usam um `php` local quando existe, ou a imagem `php:8.3-cli-alpine` pelo Docker. `PHP_TEST_IMAGE` substitui a imagem.
- **FreeBSD para o empacotamento** — `npm run deploy` só roda no FreeBSD, com `PFSENSE_PORTS_DIR` apontando para um checkout do FreeBSD-ports do pfSense.

## Verificar, preparar e empacotar \{#check-stage-and-package}

Execute estes comandos a partir da raiz do repositório:

```bash
# Lint and type-check the scripts, run the PHP and Vitest suites, and validate the port.
npm run check --workspace pfsense-pkg-ipv6-prefix-updater

# Copy the port into packages/ipv6-prefix-updater/build/port with the workspace version.
npm run build --workspace pfsense-pkg-ipv6-prefix-updater

# Build the package on FreeBSD into packages/ipv6-prefix-updater/build/release.
PFSENSE_PORTS_DIR=/path/to/FreeBSD-ports npm run deploy --workspace pfsense-pkg-ipv6-prefix-updater
```

- A preparação transforma `port/Makefile.template` em `build/port/Makefile` e grava nele a `version` de `packages/ipv6-prefix-updater/package.json`.
- O empacotamento copia o port preparado para `sysutils/pfSense-pkg-Ipv6PrefixUpdater` no checkout dos ports, executa `make package` e remove essa cópia em seguida. Ele para se o destino já existir.
- Depois disso, `build/release` contém o `.pkg` com versão, uma cópia chamada `pfSense-pkg-Ipv6PrefixUpdater.pkg` e um arquivo `.sha256` para cada um, contendo apenas o hash.

## Workflow de release \{#release-workflow}

O job `publish-pfsense-packages-ipv6-prefix-updater` em `.github/workflows/nova-publish-project.yml`, gerado pelo Nova, roda no workflow de publicação:

1. Valida e prepara o port em um runner Ubuntu.
2. Quando o secret `PFSENSE_RELEASE_SIGNING_KEY` está definido, deriva a chave pública de `PFSENSE_RELEASE_SIGNING_KEY` e a adiciona a `usr/local/share/pfSense-pkg-Ipv6PrefixUpdater/release-signing.pub` no port preparado.
3. Gera o pacote no FreeBSD com o checkout configurado do FreeBSD-ports do pfSense.
4. Quando o secret está definido, assina cada `.pkg` como `<file>.pkg.sig` com `ssh-keygen -Y sign -n pfSense-pkg-Ipv6PrefixUpdater`.
5. Envia pacotes, checksums e assinaturas como um artefato do workflow mantido por 7 dias e anexa os mesmos arquivos à release.

O build marca o pacote para qualquer versão do FreeBSD porque ele não contém código compilado, portanto um único pacote pode ser instalado em todas as versões compatíveis do pfSense. `PFSENSE_FREEBSD_VERSION` seleciona apenas a versão do FreeBSD usada pela VM de build. O comando `pkg add` do guia de instalação baixa `pfSense-pkg-Ipv6PrefixUpdater.pkg` da release que o GitHub marca como mais recente.

## Assinatura de release \{#release-signing}

A única configuração de assinatura é o secret de repositório `PFSENSE_RELEASE_SIGNING_KEY`, que contém uma chave privada OpenSSH Ed25519 sem criptografia.

1. No 1Password, escolha **New Item → SSH Key → Generate a New Key → Ed25519**.
2. No campo da chave privada, escolha **Export**, selecione o formato OpenSSH e não defina uma senha.
3. Verifique a área de transferência antes de salvar o secret:

   ```bash
   pbpaste | head -1
   ```

   O comando deve exibir `-----BEGIN OPENSSH PRIVATE KEY-----`.

4. Envie a área de transferência diretamente ao GitHub ou leia um arquivo exportado:

   ```bash
   pbpaste | gh secret set PFSENSE_RELEASE_SIGNING_KEY
   gh secret set PFSENSE_RELEASE_SIGNING_KEY < <file>
   ```

5. Exclua o arquivo da chave privada exportada depois de salvar o secret.

Sem o secret, os pacotes não incluem uma chave pública e as releases não são assinadas. Para trocar a chave, adicione a nova chave pública `ssh-ed25519 ...` a `release-signing.pub`, publique uma release enquanto a chave antiga ainda for o secret e depois substitua o secret pela nova chave.

Se a chave de assinatura for perdida, as cópias instaladas não poderão autenticar uma release assinada pela chave substituta. Cada instalação afetada precisa usar uma vez o comando manual `pkg add -f` para instalar um pacote com a nova chave pública.

## Testar endpoints de atualização em uma VM \{#test-update-endpoints-in-a-vm}

A CLI aceita duas variáveis de ambiente apenas para testes controlados em uma VM:

- `IPV6_PREFIX_UPDATER_RELEASES_API` substitui a URL da API da release mais recente.
- `IPV6_PREFIX_UPDATER_DOWNLOAD_PREFIX` substitui o prefixo permitido das URLs dos arquivos da release.

Elas são lidas somente por `/usr/local/sbin/ipv6-prefix-updater`; nunca são salvas na configuração do pacote nem lidas diretamente pela WebGUI. Defina todas as substituições necessárias na mesma invocação da CLI:

```shell
IPV6_PREFIX_UPDATER_RELEASES_API=http://192.0.2.10/latest.json \
IPV6_PREFIX_UPDATER_DOWNLOAD_PREFIX=http://192.0.2.10/releases/ \
/usr/local/sbin/ipv6-prefix-updater --check-updates
```

Use `--self-update` em vez de `--check-updates` para testar todo o caminho de download, soma SHA-256, assinatura da release, metadados do pacote e `pkg add -f` com a release de teste.

## Suítes de testes PHP \{#php-test-suites}

- **`tests/domain.php`**: <Terminology title="A grafia curta em minúsculas, como 2001:db8::1" to="/docs/reference/terminology#addresses-and-prefixes">forma canônica</Terminology>, os limites `/48` e `/64`, aplicação de máscara, <Terminology title="Os bits depois do prefixo, sempre copiados sem alteração" to="/docs/reference/terminology#addresses-and-prefixes">bits de host</Terminology> em `/53`, endereços rejeitados, planejamento no-op, filtragem pelo prefixo anterior e uma alteração de comprimento tratada como <Terminology title="Seu prefixo mudou, então o pacote entra em ação" to="/docs/reference/terminology#baselines-and-transitions">transição de prefixo</Terminology>.
- **`tests/runtime.php`**: análise de todos os <Terminology title="Um único botão para um tipo inteiro de configuração" to="/docs/reference/terminology#fields-and-change-plans">grupos de campos</Terminology>, exceções de campos individuais, reaplicação das configurações de outros pacotes, <Terminology title="O arquivo com cada referência, mantido mesmo após reinstalar" to="/docs/reference/terminology#running-checks">estado do pacote</Terminology> atômico, o <Terminology title="Impede que duas verificações rodem ao mesmo tempo" to="/docs/reference/terminology#running-checks">bloqueio de execução</Terminology>, plataformas não suportadas e verificações agendadas desativadas. Também cobre a ordem da transação e as falhas na gravação, no backup, na verificação prévia de recarregamento, nos recarregamentos e na notificação, além do <Terminology title="O prefixo mudou, mas nenhum campo aprovado usava o antigo" to="/docs/reference/terminology#run-outcomes">Aviso</Terminology> sem correspondências.
- **`tests/pfsense-adapter.php`**: uma atualização forçada do endereço sem fallback para <Terminology title="Um endereço fe80 que nunca é usado como origem" to="/docs/reference/terminology#addresses-and-prefixes">link-local</Terminology>, o backup antes de uma gravação que não cria outro backup e um backup com falha que para antes da gravação.
- **`tests/updates.php`**: comparação de versões, processamento de releases e validação de URLs, agendamentos aleatórios estáveis, eliminação de avisos duplicados, digests da API do GitHub, fallbacks `.sha256`, processamento de chaves de assinatura, saída de allowed-signers, argumentos exatos e entrada padrão de `ssh-keygen`, assinaturas válidas, chaves e namespaces incorretos e pacotes adulterados.
- **`tests/translations.php`** e **`tests/webgui-localization.php`**: catálogos completos para cada identificador de idioma do pfSense, além do formulário de Configurações e das mensagens de validação traduzidos.

## Site de documentação \{#documentation-site}

Em `apps/docs`, `npm run check` executa o ESLint, a verificação da árvore de traduções, três verificações de tipos e as suítes do Vitest para arquivos `.env`, frontmatter, links, tabelas, links do glossário e declarações de tipos. `npm run build` gera o build de todos os idiomas.

As páginas de documentação traduzidas de cada idioma ficam em `apps/docs/i18n/<locale>/docusaurus-plugin-content-docs/current/` e espelham as páginas em inglês, então atualize-as quando uma página em inglês mudar. O texto da interface (página inicial, barra de navegação, rodapé, blog e rótulos da barra lateral) vem de `scripts/generate-locales.mjs`, que lê `scripts/locale-copies.json` e as traduções do pacote. `npm run i18n` executa esse gerador primeiro, e ele preserva as páginas de documentação traduzidas.

`.github/workflows/nova-publish-project.yml` gera o build do site e o publica no GitHub Pages quando uma release é publicada.
