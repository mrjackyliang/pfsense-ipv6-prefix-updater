# PROJECT_RULES.md

## Project Identity

### Name and Description

- **Project name:** pfSense IPv6 Prefix Updater
  (`pfsense-ipv6-prefix-updater`)
- **Description:** A pfSense package that safely follows dynamic ISP IPv6 prefix changes
  across firewall configuration.
- **Primary language:** PHP, with Nova package tooling in TypeScript and shell
- **Framework / runtime:** Nova pfSense package scaffold and the pfSense package system

### Repository URL

- **URL:** https://github.com/mrjackyliang/pfsense-ipv6-prefix-updater

## Build and Tooling

### Prerequisites

Use a Node.js version permitted by the root manifest, npm, PHP for local syntax checks,
and a disposable pfSense lab for package lifecycle and mutation verification.

### Commands

Use the root `dev`, `prod`, `check`, `build`, `deploy`, `clean`, `changelog`, and
`recipes` commands for repository-wide work. Nova orchestrates the root, package, and
documentation workspaces from the configuration in `nova.config.json`.

| Command                                                      | Purpose                                                    |
|--------------------------------------------------------------|------------------------------------------------------------|
| `npm run check --workspace pfsense-pkg-ipv6-prefix-updater`  | Check scripts, tests, and the staged package definition    |
| `npm run build --workspace pfsense-pkg-ipv6-prefix-updater`  | Stage the generated pfSense package tree                   |

### Environment Variables

The package must not depend on committed secrets. Runtime configuration belongs in the
pfSense package configuration and approved pfSense-owned storage.

## Workspace Rules

### Workspace Inventory

#### Nova Workspace Boundary

- Build the replacement package in `packages/ipv6-prefix-updater` using Nova's pfSense
  package scaffold.
- Treat `assets/legacy/update.php`, `assets/legacy/lib/`, `assets/legacy/install.sh`, and the legacy README as
  behavioral and compatibility inputs, not as the final package layout.
- Preserve the working prefix calculation and safety knowledge, but re-review every
  configuration path before allowing the package to mutate it.
- Do not keep runtime state, backups, or installed code under `/root` in the package.
- Keep the legacy installer available for comparison until package installation,
  upgrade, execution, and removal are verified.

## Architecture and Data

### Architecture

- Keep WebGUI configuration, scheduling, package lifecycle, prefix detection, change
  planning, persistence, and notification behind explicit boundaries.
- Keep pure prefix and change-planning behavior independent of a live firewall wherever
  possible.

### Data Flow and Ownership

- Read pfSense-owned configuration through supported APIs, produce and validate a
  complete change plan, create an approved backup, write once, verify, then update the
  last-successful state and notify.
- Package-owned state and locks belong in pfSense-appropriate locations; user
  configuration remains owned by pfSense.

## Project Guardrails

### Security, Privacy, and Secrets

#### Configuration Safety Invariants

- Confirm execution inside a supported pfSense environment before reading or writing
  configuration.
- Validate the configured interface and require a prefix length from 48 through 64.
- Reject a link-local, loopback, multicast, unspecified, or otherwise unsuitable address
  as the active global source.
- Acquire a lock before reading cached state or preparing changes; concurrent runs must
  exit without writing.
- Treat the last successfully applied prefix as state, not merely the previous attempted
  value.
- If the prefix is unchanged, exit successfully without writing configuration, reloading
  services, rotating backups, or sending a change notification.
- Preserve host bits exactly when constructing replacement addresses.
- Mutate only approved configuration fields with understood IPv6 semantics.
- Produce a complete change plan before the first mutation.
- Back up the current configuration through an approved pfSense mechanism before commit.
- Write once after all changes validate, verify the result, then update state and notify.
- Never leave the cache claiming success when the configuration write or required reload
  failed.

### Platform and Domain Rules

#### Package Lifecycle Rules

- Install application code, configuration metadata, services, and WebGUI files only at
  paths defined by the generated pfSense package layout.
- Use pfSense configuration APIs and conventions; do not edit `config.xml` with raw
  string replacement.
- Keep defaults conservative and make scheduled execution opt-in until required settings
  validate.
- Package install and upgrade scripts must be repeatable. They must not erase user
  settings, backups, or logs without an explicit migration rule.
- Package removal should stop schedules and remove package-owned runtime artifacts while
  preserving user configuration when pfSense conventions require it.
- Give each monitored target a stable identifier so schedule and state changes do not
  accidentally bind to list position.
- Store runtime state and locks in pfSense-appropriate locations with restrictive
  permissions.
- Keep the WebGUI thin: validate and persist settings there, while prefix detection and
  mutation remain independently testable domain logic.

#### Address and Mutation Rules

- Use binary IPv6 parsing and masking for prefix calculations; do not derive correctness
  from textual abbreviation or string prefixes.
- Canonicalize addresses for comparison while preserving the configured semantics on
  output.
- Treat prefix length as part of the state. A changed length requires the same review and
  protection as a changed address.
- Do not modify IPv4 values, link-local addresses, remote peer files, comments, secrets,
  certificates, or unrelated text that happens to contain matching characters.
- Record each planned change by approved configuration path and redacted before or after
  address; never dump the full configuration.
- Count and report changed fields. Zero planned changes after a prefix transition is a
  warning that requires operator visibility, not silent success.
- Trigger only the service reloads proven necessary for the fields that changed.

#### PHP and Shell Safety

- Keep pfSense-specific calls behind adapters where pure prefix and change-planning logic
  can be tested without a firewall.
- Escape output rendered in the WebGUI and validate every persisted setting again at
  execution time.
- Do not build shell commands by concatenating paths, interface names, addresses, or
  other configuration values.
- Prefer PHP and pfSense filesystem APIs over shelling out. When a command is unavoidable,
  use a fixed executable and safely separated arguments.
- Never log configuration secrets or include the full `config.xml` in errors,
  notifications, or test artifacts.
- Fail closed on malformed configuration, unsupported schema shapes, backup failure, or
  uncertain write state.

### Compatibility

- Maintain a tested support matrix for pfSense version, PHP version, and relevant
  configuration schema.
- Isolate compatibility shims and name the versions they support.
- Unknown configuration shapes must be skipped with a warning or stop the run according
  to their risk; they must never be guessed.
- Add fixtures from sanitized supported-version configurations for every approved
  mutation path.
- A new pfSense release is unsupported until install, upgrade, detection, backup,
  mutation, notification, and removal are verified.

## Testing and Verification

### Test Strategy

- Unit-test IPv6 parsing, masking, host-bit preservation, invalid input, and prefix-length
  boundaries.
- Test change planning with sanitized fixtures for aliases, static or virtual addresses,
  IPsec, OpenVPN, WireGuard, and every later approved path.
- Test no-op runs, first-run state, prefix change, prefix-length change, concurrent runs,
  backup failure, write failure, notification failure, and interrupted execution.
- Verify package staging, manifest completeness, permissions, installation, upgrade, and
  removal with the scripts generated by Nova.
- Use a disposable pfSense lab for end-to-end tests; never exercise configuration
  mutation against a production firewall during automated verification.
- Compare a post-write configuration with the planned change set and assert that no
  unrelated path changed.

### Required Verification

Run the root and package-workspace checks, build and stage the package, and reserve
installation, upgrade, mutation, and removal checks for a disposable pfSense lab.
